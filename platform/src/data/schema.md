# Knowledge graph data contract (`graph.json`)

`graph.json` is generated by `ingest/build_graph.py` from the labeling
workbook and is the **only** data source the app reads. Regenerate with
`npm run ingest` (or `python3 ingest/build_graph.py`).

## Why the shape is what it is

The workbook has one row per *observation* and reuses IDs across papers.
Ingest dedups those into **nodes** and derives the **edge list from the
foreign keys** — the workbook's own `Relationships` tab is an unfinished
stub (4 example rows, mismatched IDs) and is deliberately ignored.

## Node types

| Type | Role in the model | Key fields |
| --- | --- | --- |
| `paper` | Resource — the evidence anchor | `title, authors, year, venue, abstract, license, source_url, domain, labeled` |
| `discoverable` | Problem — framed as a question; the primary entry point | `statement, status, domains[], papers[]` |
| `tool` | Portable method/technique | `name, domains[], papers[], roles[]` |
| `pattern` | The bridge — a structural reason a tool fit a problem | `label, domains[], observations[]` |

`domain` is an editorial cluster (see `DOMAINS` in the ingest); it is how the
UI shows that a pattern bridge is genuinely *cross*-domain. `labeled` marks
which papers have been decomposed into graph structure vs. cataloged only.

## Edge types (derived)

| `rel` | From → To | Source in workbook |
| --- | --- | --- |
| `solves` | paper → discoverable | Discoverables tab |
| `uses` | paper → tool | Tools tab (carries `role`: Introduced/Applied) |
| `exhibits` | discoverable → pattern | Patterns tab |
| `good_for` | tool → pattern | Patterns tab |
| `applies_to` | tool → discoverable | Patterns tab (a realized tool↔problem link) |
| `variant_of` | tool → tool | parsed from "Variant of …" reviewer notes |

Every edge carries `confidence` (3 explicit / 2 implied / 1 inferred) and,
where available, a `source` excerpt — surfaced in the UI so no assertion is
shown bare.

## The gap / opportunity signal

Computed in `lib/graph/queries.ts`, not baked into the file: for a pattern
`P`, if tool `t` is `good_for P` and discoverable `d` `exhibits P` but `t` has
no `applies_to d` edge, `(t → d)` is a candidate direction of inquiry. When
`t` and `d` sit in different domains it's a cross-domain transfer suggestion —
a classical-graph-analytics stand-in for the "promising directions" the QNN
layer will eventually predict.

## Swapping the backing store

The app never imports `graph.json` directly outside `lib/graph`. Everything
goes through the `GraphStore` interface (`lib/graph/store.ts`), whose methods
are shaped like Cypher traversals. A `Neo4jGraphStore` / `SupabaseGraphStore`
can implement the same interface later with no UI changes.
